## 1. 제품 개요 & 범위

### 한 문장 정의
9급 일반행정직 수험생이 **매일 5분 드립**으로 학습 습관을 들이고, **주기적 과목별 모의고사**로 약점을 진단받아, 그 약점이 자동으로 다음 문제·용어로 **재출제**되어 합격까지 가는 안드로이드 앱.

### 핵심 목적
고객(수험생)이 9급 일반행정직 시험을 **통과**하게 만드는 것. 그 수단으로 (1) 매일 드립으로 리텐션 확보, (2) 약점 진단·집중 보강.

### 타깃 & 과목
- 타깃: 9급 일반행정직 준비생 (주로 20대)
- 과목 5개: 국어 · 영어 · 한국사 · 행정법 · 행정학

### 이미 동작 중 (재활용)
- Fastify 백엔드 + MongoDB Atlas, 익명 디바이스 인증(가입 없이 진도 저장)
- 데이터 모델: User / Question / DailySet / Progress(SRS) / Recommendation
- 드립 생성 스크립트(build-daily-set), 콘텐츠 import(멱등), 스모크 테스트
- Expo 앱: 홈 / 퀴즈 / 진도율 탭, 디자인 토큰 컴포넌트

### 이번에 새로 만드는 것
1. **과목별 모의고사 모드** — 5과목 실전형 응시 + 채점
2. **약점 진단 엔진** — 풀이 패턴(정오답·과목·단원·소요시간) 집계로 약한 영역 산출
3. **약점 기반 재출제** — 진단된 약점 영역의 유사기출·용어를 드립/추천으로 자동 주입
4. **AI 풀이·해설 생성** — OpenAI 프록시, 문제별 단계 해설 + 공용 캐싱
5. **푸시 알림** — expo-notifications, 매일 "오늘의 5문제"
6. **5년치 실제 기출 적재** — placeholder를 사이버국가고시센터 공개 기출로 교체

### 범위 밖 (나중)
- 회원가입/로그인 UI (맨 마지막) → 결제 → iOS → 타 직렬 확장

## 2. 아키텍처 & 데이터 흐름

### 구성 (3계층 + 배치 잡)
```
Expo 앱 (RN)  ── HTTPS(JWT) ──▶  Fastify API (Node)  ──┬─ Mongoose ─▶  MongoDB Atlas
  홈·퀴즈·모의고사·진도/약점         routes: auth/content/   │
  React Query, 익명 deviceId       progress/exam🆕/ai🆕    └─ 프록시 ──▶  OpenAI GPT
  expo-notifications              lib: srs/weakness🆕                    (해설 생성·캐싱)
                                  Cron 배치(1일1회): 드립세트 생성 · 공용해설 캐싱 · 푸시 트리거
```

### 하루 사이클
1. **밤(배치)**: Cron이 유저 약점(weakProfile)을 보고 **내일 드립 세트** 생성 = 신규 3 + SRS복습 2, 신규는 **약점 과목/단원 우선**. 새 문제의 **공용 해설을 OpenAI로 1회 생성→DB 캐싱**(있으면 스킵).
2. **아침(푸시)**: "오늘의 5문제" 알림 → 앱 진입.
3. **풀이**: 정오답·선택지·**소요시간** 기록 → 오답은 SRS 큐(1d/3d/7d/14d).
4. **집계(weakness 엔진)**: 과목·단원별 정답률·평균시간 집계로 **약점 점수** 갱신 (DB 집계, AI 호출 없음).
5. **주기 점검(모의고사)**: 과목별 모의고사 응시 → `examResults` 저장 → 약점 **재측정**(가중치↑) → 다음 드립 반영.
6. **해설 조회**: 캐싱된 공용 해설 즉시 표시 (AI 추가 호출 없음).

### AI vs DB 집계 — 하이브리드 (초반 AI → 점진적 집계 전환)
"데이터가 없다"는 두 층위를 모두 AI로 해결하되, **마일스톤에만** AI를 부른다.

**(a) 콘텐츠 구조 부재** → 적재 시 **AI가 문제당 1회 태깅**(과목/단원/개념/난이도/연도). 영구 캐싱. 집계의 버킷 인프라.

**(b) 신규 유저 콜드 스타트** → 시간에 따라 진단 방식이 이동:

| 단계 | 약점 진단 방식 | AI 비용 |
|---|---|---|
| **콜드** (가입~온보딩 진단고사, 풀이 적음) | AI가 틀린 문제+태그+풀이패턴 보고 약점 추론 | 유저당 1~2회 |
| **웜** (데이터 충분) | DB 집계(정답률·소요시간), AI는 모의고사 직후에만 보조 | ≈0 |

**원칙**: AI는 "매 풀이마다"가 아니라 **① 문제 태깅(1회) ② 콜드 유저 진단(온보딩) ③ 모의고사 직후 재측정** 세 군데에만. 평소 갱신은 DB 집계 → 초반 정확도 + 장기 저비용.

### 설계 원칙 (비용·격리·보안)
- AI 비용 최소화: 공통 콘텐츠(해설)는 1회 생성·전체 공유 캐싱. 약점 계산은 DB 집계 기본.
- 모듈 격리: `weakness`(집계) · `exam`(모의고사) · `ai`(해설 프록시)를 독립 라우트/라이브러리로 분리.
- 키 보안: OpenAI 키는 백엔드에만. 앱은 직접 호출 금지.

## 3. 데이터 모델 (기존 5개 확장 + 신규 2개)

### 기존 컬렉션 (유지 + 필드 추가)
- **users** — 익명 deviceId 기반(가입은 나중). 🆕 `weakProfile` 약점 요약 캐시 필드 추가
- **questions** — 🆕 태그 필드: `subject` · `unit` · `concept` · `difficulty` · `year` · `explanationId`(해설 참조)
- **dailySets** — 유지 (신규3+복습2, 약점 우선 주입)
- **progress** — 유지 + `timeSpentMs`(소요시간), SRS 필드
- **recommendations** — 유지 (약점 기반 추천 항목)

### 신규 컬렉션 2개
- 🆕 **examResults** — 과목별 모의고사 기록: `subject · answers[] · score · perUnitStats · takenAt`. 약점 재측정 입력.
- 🆕 **explanations** — AI 해설 **공용 캐시**: `questionId(unique) · steps[] · model · createdAt`. 한 번 생성 후 전체 유저 공유.

### 약점 저장 방식
별도 컬렉션 대신 **`users.weakProfile`에 캐시**:
- 형태: `[{ subject, unit, score(0~100), basis: 'ai'|'aggregate', updatedAt }]`
- 평소엔 집계로 갱신, 마일스톤엔 AI로 갱신. `basis`로 출처 추적.
- 효과: 신규 컬렉션을 2개로 최소화, 동작 중인 백엔드를 크게 흔들지 않음.

## 4. 빌드 순서 (Phase)

각 단계는 끝나면 실제 동작 검증(verification) 후 다음으로 진행.

### Phase 0 — 토대 점검 + 실제 기출 적재 파이프라인 ⭐최우선
- 기존 server/app 실행 재확인(스모크 통과)
- 5년치 실제 기출 → JSON 적재 + AI 태깅(과목/단원/개념/난이도/연도)
- **리스크**: 기출 원본 확보·파싱(사이버국가고시센터 PDF)이 핵심 자산이자 가장 손 많이 가는 부분. 1순위.

### Phase 1 — 핵심 루프(드립 + 약점)
- 약점 엔진(DB 집계) + 콜드스타트 AI 진단(온보딩 진단고사)
- 드립 세트에 약점 과목/단원 우선 주입 (build-daily-set 확장)
- `users.weakProfile` 갱신 로직

### Phase 2 — 주기 점검(과목별 모의고사)
- 모의고사 응시·채점 화면 + `examResults` + 약점 재측정

### Phase 3 — AI 해설
- OpenAI 프록시 라우트 + `explanations` 공용 캐시 + 해설 UI

### Phase 4 — 리텐션(푸시 알림)
- expo-notifications, 매일 "오늘의 5문제" + Cron 발송 트리거

### Phase 5 — 맨 마지막
- 회원가입/로그인 UI(익명→이메일 승격, userId 유지로 진도 보존), 그다음 결제
